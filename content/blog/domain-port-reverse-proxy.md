## 问题

> *用 AI 做了几个网页或者网页端的 app，上传服务器时，有没有想过，是把所有 app 放在一个域名 `xxxxxx.com` 下，通过 `xxxxxx.com/aaaa`、`xxxxxx.com/bbbb` 这种模式，还是分别使用一个端口比如 `aaaa.xxxxxx.com`、`bbbb.xxxxxx.com` 这种模式好呢？这两种模式有什么优缺点？*

### 先说结论

上面所提到的问题，其实分两个层面：

- **对外暴露**：（别人浏览访问）怎么让人访问到你
- **对内运行**：（服务器内部分配）进程实际监听在哪

这两个层面可以解耦。下面逐个分析。

**最佳实践：对外用一个 IP + 一个端口（80/443），用反向代理（Nginx/Caddy/Traefik）按域名分发到内部不同端口。也就是 `aaaa.xxxxxx.com`、`bbbb.xxxxxx.com` 这种模式。**

---

## 方案对比

| 方案 | 对外 | 内部 | 典型用途 |
|---|---|---|---|
| A. 每个 app 一个端口 | ip:8001, ip:8002 | 各自监听 | 内网/测试/自用 |
| B. 每个 app 一个子 IP | 1.2.3.4, 1.2.3.5 都用 80 | 各自监听 | 需要独立 IP 的场景 |
| C. 一个端口 + 路径区分 | ip/app1, ip/app2 | 一个服务或反代 | 同源小型应用 |
| D. 一个端口 + 域名区分（推荐） | a.com, b.com 都走 443 | 反代到内部端口 | 生产环境 |

---

## A. 每个 App 独立端口（很少用，同 IP 测试用）

```
http://1.2.3.4:8001   -> app1
http://1.2.3.4:8002   -> app2
```

**优点**
- 部署最简单，进程直接监听各自端口
- 应用之间天然隔离，一个崩了不影响另一个
- 不需要域名，不需要反代

**缺点**
- 用户要记端口，体验差
- **SSL 证书几乎没法搞**：一张证书绑一个端口，多端口要么每个端口一套证书，要么放弃 HTTPS
- 防火墙要开一堆端口，安全隐患大
- CORS / Cookie 跨端口共享麻烦（端口不同算不同源）
- 端口号容易被扫描、被墙

**适合**：内网服务、临时测试、给开发自己用的工具。

---

## B. 每个 App 一个子 IP（用不到）

```
1.2.3.4:80 -> app1
1.2.3.5:80 -> app2
```

**优点**
- 每个 app 都占标准 80/443，用户体验统一
- 完全隔离，证书、Cookie、CORS 都互不影响

**缺点**
- **公网 IPv4 要花钱**，云厂商一个弹性 IP 一个月几块到几十块，还很难申请
- 服务器要配多网卡 / 多 IP 别名，运维复杂
- IPv4 枯竭，大多数云现在只给你 1 个公网 IP
- 完全不 scale，10 个 app 要 10 个 IP

**适合**：极少数必须独立 IP 的场景（比如某些白名单对接、邮件服务器反解）。

---

## C. 一个端口 + 路径区分

```
https://example.com/app1/
https://example.com/app2/
```

**优点**
- 一个域名、一张证书、一个端口
- 没有 CORS 问题（同源）

**缺点**
- 每个 app 必须支持配置 **base path**（很多框架改起来很痛苦，静态资源路径、路由都要适配）
- 前端路由（React Router 的 history 模式）经常出问题
- Cookie 作用域在整个域名下，隔离性差
- 一个 app 出问题可能影响整站

**适合**：你自己写的、能控制 base path 的小应用；不推荐给第三方成品。

---

## D. 一个端口 + 子域名 + 反向代理 ⭐推荐

```
a.example.com  ─┐
b.example.com  ─┼─> Nginx (443) ──> 127.0.0.1:8001 (app1)
c.example.com  ─┘                  └> 127.0.0.1:8002 (app2)
```

**对外**：1 个 IP，1 个端口（443）
**对内**：每个 app 还是各自监听本地端口，只是不对公网开放

**优点**
- 用户只看到域名，干净、好记
- **一张泛域名证书 `*.example.com` 全搞定 HTTPS**
- 每个 app 是独立源，Cookie/CORS 天然隔离
- 应用完全不用改代码，进程还是监听自己的端口
- 防火墙只开 443，内部端口全部 `127.0.0.1` 绑定，安全
- 加新 app 只需加一段 Nginx 配置，不动网络层
- 好做限流、鉴权、日志、灰度、WebSocket 转发
- 完美适配 Docker / Compose（每容器一个端口，反代统一出口）

**缺点**
- 需要域名（几块钱一年）和 DNS 泛解析
- 多一层反代，配置初期要学一点 Nginx/Caddy
- 反代本身要维护（Caddy 自动证书，最省心）

**适合**：生产环境、多个 web app 的标准做法。

---

## 一句话总结

> **端口和 IP 是「对内」的事，域名和 443 是「对外」的事。**
> 对外永远只暴露 `443`，对内随便你怎么分端口，中间用反向代理把内外接起来。
